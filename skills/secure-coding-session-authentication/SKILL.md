# Session & authentication management

Decision rules for issuing, storing, and expiring session state and
credentials. Research trail: layer 1 (OWASP Session Management Cheat
Sheet) plus layer 2 (ASVS V3 "Session Management" chapter, CWE-384
Session Fixation).

## Trigger

Use when a design or review is deciding how a session identifier is
issued, stored, cached, timed out, or resumed across tabs/devices —
cookie flag selection, storage location, timeout tiering, or
session-fixation-prone resume flows. Do not use it for the
access-control decision of what an authenticated identity may do (that
is `secure-coding-authorization-access-control`).

## Procedure

1. Cite rule 1 when a user's privilege level changes, to regenerate the
   session identifier immediately rather than keep the pre-change ID
   live.
2. Cite rule 2 when issuing a session cookie over HTTPS, to set Secure
   and HttpOnly unconditionally.
3. Cite rule 3 when choosing a `SameSite` value for a session cookie, to
   choose Strict or Lax, never None without Secure, and never rely on
   the browser default.
4. Cite rule 4 when setting an idle timeout, to tier it by session
   value — 2-5 minutes for high-value sessions, 15-30 minutes for
   low-risk ones.
5. Cite rule 5 when implementing session expiry, to enforce both idle
   and absolute timeouts server-side rather than client-side-only.
6. Cite rule 6 when choosing where to store an auth token in a browser
   client, to choose an HttpOnly cookie or backend-for-frontend pattern
   and remove any existing Web Storage token storage.
7. Cite rule 7 when a session ID currently arrives via URL query
   parameter, to remove that acceptance path and require the cookie
   mechanism only.
8. Cite rule 8 when a response carries a session identifier, to set
   `Cache-Control: no-store` on that response.
9. Cite rule 9 when designing multi-tab or multi-device session support,
   to require re-authentication or a server-issued linking token rather
   than accept an arbitrary client-supplied session ID.

## Output shape

A session-management verdict: the regeneration/cookie-flag/timeout
choices with their rule citations, any Web-Storage or URL-carried
session ID flagged for removal, and — for multi-device/tab support — the
re-authentication or linking-token mechanism chosen instead of a
client-supplied session ID.

## Rules

1. When a user's privilege level changes (login, password change, role
   elevation), regenerate the session identifier immediately — "the
   session ID must be renewed or regenerated by the web application
   after any privilege level change within the associated user
   session." Do not keep the pre-authentication session ID live
   post-login. source:
   https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html

2. When issuing a session cookie over HTTPS, set **Secure** and
   **HttpOnly** unconditionally — Secure blocks plaintext transmission,
   HttpOnly blocks `document.cookie` reads, and "the session ID must
   not be exposed" to script even when other XSS defenses fail.
   source: https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html

3. When choosing a `SameSite` value for a session cookie, choose
   `Strict` (or `Lax` when cross-site GET navigation into an
   authenticated view is required) — never `None` without also setting
   `Secure`, and never rely on the browser default. source:
   https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html

4. When a session is high-value (financial, admin), set idle timeout to
   2-5 minutes; for low-risk sessions, 15-30 minutes is acceptable —
   timeout length is a risk-tiered choice, not a single constant across
   an application. source:
   https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html

5. When implementing session expiry, enforce both idle and absolute
   timeouts **server-side** — "session timeout management and
   expiration must be enforced server-side," because a client-side-only
   timer is trivially bypassed by replaying the cookie after tampering
   with client clock/state. source:
   https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html

6. When choosing where to store an auth token in a browser client,
   choose an HttpOnly cookie or a backend-for-frontend pattern, and
   **REMOVE** any existing `localStorage`/`sessionStorage` token
   storage — Web Storage is script-readable, so any XSS on the page
   becomes full session takeover, a strictly worse blast radius than an
   HttpOnly cookie under the same XSS. source:
   https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html

7. When a session ID currently arrives via URL query parameter (a
   legacy pattern), **REMOVE** that acceptance path and require the
   cookie mechanism only — URL-carried session IDs leak via browser
   history, referrer headers, and server logs, an exposure the cookie
   mechanism does not have. source:
   https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html

8. When a response carries a session identifier (login response, session
   refresh), set `Cache-Control: no-store` on that response — caching a
   session-bearing response lets a shared/proxy cache replay another
   user's session ID to a later requester. source:
   https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html

9. When designing multi-tab or multi-device session support, do not
   accept an arbitrary client-supplied session ID as a way to "resume" a
   session — require re-authentication or a server-issued linking token
   instead, since accepting client-chosen IDs re-opens the session
   fixation defect CWE-384 describes. source:
   https://cwe.mitre.org/data/definitions/384.html
