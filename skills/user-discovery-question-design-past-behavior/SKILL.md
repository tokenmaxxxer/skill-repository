# Question design: past behavior over hypotheticals/opinion/pitching

Research trail: Rob Fitzpatrick, *The Mom Test* (three-rule summary and worked examples); UXtweak and koji.so 2026 explainer pieces on Mom-Test-style bias avoidance; behavioral-interviewing literature contrasting behavioral vs. attitudinal question evidence value. All searched this session.

## Trigger

Apply this skill when drafting a discovery-interview question or
reviewing/sequencing a script — whether a candidate question invites
hypothetical/opinion fiction, whether the pitch is sequenced after the
behavioral questions, and which hypothesis's questions go first —
distinct from how deep to follow up on the answer once asked
(follow-up-ladder-depth).

## Procedure

1. Draft each question around a specific past event rather than a
   hypothetical or generic phrasing (rule 1).
2. Rewrite any "would you"/"do you think" question into a past-event
   question, or drop it (rule 2).
3. Do not describe the idea/product before asking the behavioral
   question (rule 3).
4. Ask "how are you solving this today" / "when did this last cost you"
   rather than a direct problem-confirmation question (rule 4).
5. Let the interviewee finish, then follow with a clarifying behavioral
   probe rather than filling silence with your own explanation (rule 5).
6. Phrase a specific-claim check as a request for a recent concrete
   example rather than an agree/disagree prompt (rule 6).
7. Sequence every hypothesis's behavioral questions before any question
   that reveals or pitches the solution (rule 7).
8. Drop any rating/agreement-scale question from a discovery script
   (rule 8).
9. Remove any feature description or demo that front-loads the script
   ahead of a current-behavior question (rule 9).
10. When testing more than one hypothesis, rank them by which one would
    kill the idea if disconfirmed, and script that one's behavioral
    questions first (rule 10).

## Output shape

An interview script (or a review verdict on one) in which every
question is anchored to a specific past event, no hypothetical/opinion
or pitch/demo content precedes the behavioral questions for any
hypothesis, and the fatal-first hypothesis is scripted earliest.

## Rules

1. When drafting an interview question, ask about a specific past event ("when was the last time X happened," "walk me through what you did") rather than a hypothetical or generic ("would you," "do you usually") — specific-past-event questions are objective data while hypothetical/generic questions invite fiction, per the Mom Test's core past-vs-hypothetical rule. source: https://blog.uxtweak.com/the-mom-test/

2. When a candidate question contains "would you" or "do you think," rewrite it to ask what the person actually did the last time the situation arose, or drop the question — future-intention framing produces stated intentions, and intentions are a poor substitute for behavior. source: https://www.ventureforall.com/p/from-assumptions-to-evidence-are

3. When you are tempted to describe your idea/product before asking a behavioral question, do not — ask about the person's life and current workarounds first; describing the idea before the behavioral question primes a polite/flattering answer instead of an evidence-bearing one (the "mom" framing: even someone who loves you can't tell you what you want to hear if the question is only about her own life). source: https://blog.uxtweak.com/the-mom-test/

4. When you want to know if a problem is real, ask "how are you solving this today" and "when did this last cost you time/money" rather than "is this a problem for you" — a direct problem-confirmation question invites a socially agreeable yes, while a current-solution/cost question forces a concrete, checkable answer. source: https://www.koji.so/blog/mom-test-customer-interviews-2026

5. When the interviewee starts speaking, let them finish and follow with a clarifying behavioral probe rather than filling silence with your own explanation — "talk less and listen more" is the third Mom Test rule specifically because interviewer talk-time displaces the behavioral data the interview exists to collect. source: https://blog.uxtweak.com/the-mom-test/

6. When you need to test a specific claim ("no one uses feature X"), phrase the check as a request for a recent concrete example ("tell me about the last time you needed X") rather than asking the person to agree/disagree with the claim directly — agreement/disagreement questions are vulnerable to acquiescence bias, concrete-example requests are not. source: https://www.ventureforall.com/p/from-assumptions-to-evidence-are

7. When scripting the interview, sequence every hypothesis's behavioral questions before any question that reveals or pitches the solution — once the interviewee knows what you're building, all subsequent answers are contaminated by a desire to be helpful/positive, so the behavioral data must be collected while they are still blind to the solution. source: https://blog.uxtweak.com/the-mom-test/

8. **REMOVAL**: When an interview script contains a rating/agreement-scale question ("how likely are you to use this, 1-10"), drop it from a discovery interview script — a numeric-opinion question produces an attitudinal artifact with no behavioral grounding and is exactly the kind of "would you" fiction the Mom Test's past-behavior rule warns against; move it to a later validation-stage survey instrument instead. source: https://blog.uxtweak.com/the-mom-test/

9. **REMOVAL**: When an interview script front-loads a feature description or demo before any current-behavior question, remove the pitch from the front of the script — a description given before the behavioral baseline is established collapses the interview into a pitch-and-react session instead of a discovery session, forfeiting the "blind to the solution" evidence quality rule 7 depends on. source: https://blog.uxtweak.com/the-mom-test/

10. When a study is testing more than one hypothesis, rank them by which one, if disconfirmed, kills the underlying idea outright, and script that hypothesis's behavioral questions first — running hypotheses in an arbitrary or convenience-driven order risks spending the whole saturation budget confirming a minor assumption while the fatal one goes untested, so the order itself is a design decision, not an afterthought.
